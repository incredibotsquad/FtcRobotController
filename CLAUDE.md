# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

FTC (FIRST Tech Challenge) robot controller app for the BIOBUZZ 2026-2027 season, built on the official FTC SDK 12.0. It's an Android app. All team code lives in the `TeamCode` module. `FtcRobotController` is the SDK module and should be left alone except for pulling in upstream SDK updates. Its `external/samples` folder holds reference OpModes you can copy into TeamCode.

## Open work

`TODO.md` (repo root) lists open items: laser counting follow-ups, loop-time checks, pre-competition cleanup. Read it when picking up work, add new items there, and check items off when done.

## Build

- `./gradlew :TeamCode:assembleDebug` builds the APK. Use this to check that changes compile.
- `./gradlew installDebug` installs to a connected Robot Controller (Control Hub over adb/Wi-Fi).
- There are no unit tests and no lint setup. You can only verify behavior on the physical robot.
- Don't edit `build.common.gradle` or the top-level `build.gradle`; the SDK owns them. Add team dependencies to `TeamCode/build.gradle` or `build.dependencies.gradle`. The latter already has the extra Maven repos (bylazar, dairy.foundation).

## Libraries

- **FTCLib** (`org.ftclib.ftclib:core`): command-based framework. Subsystems extend `SubsystemBase`, and `periodic()` runs each loop through the `CommandScheduler`. Uses FTCLib hardware wrappers (`MotorEx`, `SimpleServo`) and geometry (`Pose2d`, `Rotation2d`, `Translation2d`).
- **Pedro Pathing 3.0** (`com.pedropathing:revhub`, `com.pedropathing:tuning`): path following. Uses its own `com.pedropathing.math.Pose`, which is a different type from FTCLib's `Pose2d`.
- **Panels** (`com.bylazar:fullpanels`): dashboard. `@Configurable` exposes a class's `public static` (non-final) fields for live tuning. Subsystems take a Panels `TelemetryManager` (not the SDK `Telemetry`).

## Architecture

- `Incredibot.java`: the robot container (extends FTCLib `Robot`). Its constructor builds every subsystem and turns on bulk caching for the hubs. `initTeleop()`/`initAuto()` reset the `CommandScheduler`, register the subsystems in order (Drive before Odometry), and set the default commands: `DriveRobotCommand`, `CloseGateCommand` (gate), `SmartIntakeCommand` (intake) and `LaunchReadinessCommand` (launcher). TeleOp binds the operator buttons: X toggles moving-shot compensation, START toggles the turret lock (`LaunchSubsystem.isLaunchReadinessLocked`, unlocked by default (PR #14 had made it locked; changed back on 2026-11-18). Operator START locks it: the turret parks at `TURRET_MID` and shots are aimed with the drivetrain; `initAuto()` also clears it, so autos always auto-aim with distance-based RPM; while locked the RPM and gains also come from the `LaunchReadinessCommand.LOCKED_SHOT_DISTANCE_IN` (51.0 in, the tested 2679 RPM shot) instead of the real distance), BACK (hold) reverses the intake, RB runs `LaunchBallsCommand`, LB runs `RelocalizeCommand` (resets the pose to the stance in the corner nearest the odometry position, heading 0 or 180), the left stick button runs it in `ALLIANCE_STANCE` mode (always our GARDEN corner, `Poses.RED_RELOCALIZE_STANCE` rotated for blue per `CrossOpModeStorage.allianceColor`, ignoring odometry: the fallback after a mid-field LB press), A toggles the intake bar, the right stick button turns Limelight relocalization on / off (`LaunchRelocalizeCommand.toggle()`, with a banner; `RelocalizeWithLimelightCommand`, the one-shot manual relocalize, is no longer bound). TeleOp schedules `LaunchRelocalizeCommand` in the background: during every launch at standstill it collects 5 clean Limelight frames from our HIVE and resets odometry X/Y when the launch ends (heading kept; `ENABLED`, on). For the autos it runs only if `ENABLED_IN_AUTO` (off) is true at START. Its state is always on the Driver Station ("LL relocalize": OFF, or ON with what it is doing and the last result). Neither runs in INIT any more, and `TurretVisionCorrection` drops its correction when odometry jumps (`POSE_JUMP_RESET_IN`). `initAuto()` sets the preload count to 4 and resets `HiveState`. `DRIVE_ONLY_MODE` (set in Panels before INIT) registers only Drive and Odometry and parks the turret at `TURRET_MID`.
- `subsystems/`: one FTCLib subsystem per mechanism (Drive, Intake, IntakeBar, LaunchGate, Launch, Odometry, Limelight), plus `PowerMonitorSubsystem` (logs hub voltage/current and per-motor current with tag `PowerLog`, one hub read per loop, so a line's values come from different loops ~0.2 s apart; `ENABLED`). Each constructor takes `(HardwareMap, TelemetryManager)`, except `OdometrySubsystem`. Hardware device names are string literals in the constructors and must match the Robot Controller configuration on the robot.
  - `DriveSubsystem` runs everything through Pedro's `Follower` (from `pedro/Constants.create()`), which is the only owner of the drive motors and the Pinpoint. Its `periodic()` calls `follower.update()`. `DriveRobotCommand` drives with `follower.manual()` (forward, strafe left, turn CCW). While `LaunchBallsCommand` runs it holds the robot's pose (`follower.hold`) against defense. Moving a stick breaks out of the hold. `DriveSubsystem.LAUNCH_HOLD_ENABLED` switches the feature, and it is off by default (since 2026-11-18).
  - `OdometrySubsystem` reads the pose from `DriveSubsystem` rather than the Pinpoint. It is constructed with `(DriveSubsystem, TelemetryManager)` and must be registered after `DriveSubsystem` (FTCLib runs `periodic()` in registration order). Its `periodic()` copies the pose, estimates velocity and acceleration, and writes the pose to `CrossOpModeStorage`. Pose resets go through `follower.setPose()`. Pinpoint pod offsets live in `pedro/Constants.localizerConfig`. `updatePoseFromLimelight` applies vision corrections from `RelocalizeWithLimelightCommand`.
  - `LimelightSubsystem` (Limelight 3A, fixed to the chassis) uses each HIVE tag's robot-space position, not MegaTag, because the tags move when a HIVE TIPS. Tag height tells whether a CELL is up or down and updates `HiveState`. Tag geometry is in `common/HiveTags`. The SDK's target pose in robot space has camera-style axes (x right, y down, z forward), so forward = z, left = -x, up = -y (`ROBOT_SPACE_CAMERA_AXES`, verified 2026-11-19); the Limelight UI camera pose is 5.0 in forward, 11.5 in up, pitch +40 deg. `DriveSubsystem.isEffectivelyStationary()` gates when that relocalization runs.
  - `LaunchSubsystem` runs a dual flywheel (PID + `SimpleMotorFeedforward`, RPM converted to ticks/sec using GoBILDA BARE CPR) and a turret servo (goBILDA 5-turn, 1800°, `GEAR_RATIO = 82/24`). Above `FLYWHEEL_BANG_BANG_THRESHOLD_RPM` below target it runs bang-bang. Feedforward is voltage-compensated. Gains come from a gain table indexed by distance (`GAIN_TABLE_*`). There is no adjustable visor/hood. `LaunchReadinessCommand` runs every loop: it picks the target, leads it for moving shots when enabled, aims the turret, spins the flywheel from the `SHOT_DISTANCES_IN`/`SHOT_RPMS` table (tuning points at 47 / 52 / 66 / 84 in; outside them the RPM is extrapolated from the two nearest rows, `EXTRAPOLATE_SHOT_RPM`, limited to `MIN/MAX_SHOT_RPM`, and the shot still counts as ready; gains hold the end row), and calls `setShotSolutionReady`/`setShotPossible`. The turret aims from the odometry position plus a small smoothed Limelight correction (`TurretVisionCorrection`, `ENABLED`): only from our HIVE's tags, only on clean frames (≥ `MIN_TAGS`, spread ≤ `MAX_SPREAD_IN`, within `MAX_CORRECTION_IN` of odometry, robot slow and not turning fast), held `HOLD_MS` then faded out over `FADE_MS` without them; odometry's pose is never changed, and the RPM distance uses the corrected position too (`CORRECT_DISTANCE`, on since 2026-11-19; limits `MAX_SPREAD_IN` 3 in, `MAX_CORRECTION_IN` 12 in). Servos give no feedback, so it decides the turret has settled from an estimate based on `TURRET_SERVO_RPM`. The turret check inside `isReadyToLaunch()` always passes because it compares the commanded position to itself. `periodic()` sets the alignment indicator light from the result.
  - `IntakeSubsystem` drives the intake motor and the transfer motor (the sweeper servos were removed). Sensors 1 (entrance) and 4 (top) are goBILDA laser distance sensors on analog ports, each read by `LaserBallCounter` (episode/seam/duration rules; thresholds re-tuned with `LaserIntakeTuner`). Count = entered − left: balls arriving at sensor 1 with the intake forward, minus balls that passed sensor 1 with it reversed, minus balls that passed sensor 4 while launching with the transfer forward. Sensor 1 blocked for `JAM_MS` while intaking means full. Sensor 2 (digital beam break) blocked for `SENSOR2_FULL_MS` with the transfer forward (not launching/reversing) raises the count to 4: with 4 POLLEN the last one rests there (no `FULL_RUN_ON_MS` run-on then). Sensor 3 can raise it to `SENSOR3_MIN_COUNT` the same way (`SENSOR3_MIN_ENABLED`, off). Sensor 4 blocked for `SENSOR4_LEFTOVER_MS` while not launching or reversing raises a count of 0 to 1 (`SENSOR4_LEFTOVER_ENABLED`): a launch that fed n−1 of n but counted n exits leaves that ball at sensor 4. All three only raise the count. Each laser needs its clear-background distance in `SENSOR1_BASELINE_MM`/`SENSOR4_BASELINE_MM` (0 = first reading at INIT, wrong if a ball is in front then); the duration rule is on for sensor 1 and off for sensor 4 (`SENSOR*_DURATION_RULE`: overcounting exits would let in a 5th, G407). It stops itself when full (`MAX_ARTIFACTS = 4`): after `FULL_RUN_ON_MS` `SmartIntakeCommand` enters FULL, reverses the intake motor (not the transfer) for `FULL_EJECT_MS` (`startFullEject()`) to push out a straddling 5th (balls pushed past sensor 1 then aren't subtracted), then stops it; the transfer stops `TRANSFER_FULL_DELAY_MS` after entering FULL. A launch hitting `MAX_FIRE_MS` resets the count to 0 if the transfer fed forward with sensors 1 and 4 clear for `EMPTY_CONFIRM_MS` (`confirmEmptyAfterLaunch()`); every count change is logged with tag `IntakeCount`, laser episodes with `LaserBallCounter`. The intake motor (not the transfer) has a `StallGuard` (off by default, `STALL_DETECTION_ENABLED`): a stall (low-pass filtered current (`STALL_CURRENT_FILTER_MS`) ≥ `STALL_CURRENT_A`; or low encoder speed with `STALL_SIGNAL = VELOCITY`; or both at once with `BOTH`) for `STALL_TIME_MS` while commanded forward and not launching reverses it for `UNJAM_REVERSE_MS`, up to `UNJAM_MAX_TRIES` per `UNJAM_WINDOW_MS`, then pauses `UNJAM_GIVE_UP_MS`. Intake-motor writes go through the guard (`request()`), so commands' powers are reapplied after an unjam; stop/reverse requests cancel it. Logged with tag `IntakeStall`. Transfer jam protection (`JAM_DETECTION_ENABLED`, off by default since 2026-11-20): filtered transfer current ≥ `JAM_CURRENT_A` for `JAM_CURRENT_MS`, or (launching) sensor 4 blocked with no exit for `JAM_NO_EXIT_MS`, latches a jam: transfer and intake can't run forward, `LaunchBallsCommand` ends / refuses (`EndReason.JAMMED`), `LaunchReadinessCommand` stops the flywheel and holds the turret (`setHaltWhen`), only the drive keeps running; holding the operator reverse (BACK) for `JAM_CLEAR_REVERSE_MS` clears it. Banner + DS line, tag `IntakeJam`; `LaunchShot` logs the transfer peak current per launch. `SmartIntakeCommand` switches between the LAUNCHING, INTAKING and FULL states based on whether the gate is open. `LaunchBallsCommand` commands the intake bar up (without waiting for it) and keeps it up during the launch, and opens the gate until the robot is empty. Built with the `LaunchSubsystem` (every call site does), it first waits for a steady flywheel (`WAIT_FOR_STEADY_FLYWHEEL`: both motors within `STEADY_TOLERANCE_RPM` of target, not bang-bang, for `STEADY_MS`; fires anyway after `MAX_STEADY_WAIT_MS`) and logs the speed at the gate opening and at each exit (tag `LaunchShot`). `LaunchBallsCommand.SIMPLE_LAUNCH` (default off since 2026-11-18, so the kick is active; on = a plain forward feed until the count reads 0 for `CLEAR_MS` or `MAX_FIRE_MS`, the same for any artifact count). With it off, the kick runs (`KICK_ENABLED`): the transfer reverses briefly (`KICK_REVERSE_MS_BY_COUNT`, shorter for more artifacts) while the intake runs forward to keep the stack in, then feeds forward at full power. With `REVERSE_BEFORE_GATE` (on) the reverse starts on the press with the gate still closed (an opening gate can catch in the holes of the artifact resting on it); the gate opens `GATE_OPEN_DELAY_MS` into the reverse once the flywheel is steady (the steady wait runs alongside, and a flywheel already steady before the press counts, tracked in `LaunchSubsystem`), and the feed waits `MIN_GATE_LEAD_MS` after the gate only if it opened late; with optional sensor-4 retries for a lone ball (`SINGLE_BALL_HANDLING_ENABLED`) and an optional last-ball kick (`LAST_BALL_KICK_ENABLED`), both off since 2026-11-18: every count, 1 included, gets just its `KICK_REVERSE_MS_BY_COUNT` reverse, and the launch ends when the count reads 0 for `CLEAR_MS`. Counting ignores sensor 1 and the jam rule while launching. After a kick reverse, sensor-4 exits only count once the transfer has fed forward for `KICK_EXIT_GUARD_MS` (the reverse pulls the top ball down off sensor 4, which used to count as a launch); with the count at 0, sensor 4 blocked for `LAUNCH_STUCK_BALL_MS` while launching raises it back to 1 (a ball fell back short of the flywheel), and a launch ends only after the count is 0 and sensor 4 clear for `CLEAR_MS` (500). `LaunchBallsCommand.LOG_RPM_TRACE` (off) logs the flywheel RPM per loop (tag `LaunchTrace`). Sensor states only update inside `periodic()`, so test OpModes must call it.
  - `IntakeBarSubsystem` uses two mirrored positional servos (`intakeBarLeftServo`/`intakeBarRightServo`, the former sweeper ports) to drop a bar in front of the robot for pulling POLLEN out of a FLOWER's bottom opening (G418: POLLEN only). Each servo has its own RAISED/LOWERED positions, and `setBarFraction()` moves both by the same fraction so they don't fight. Auto no longer lowers the bar at the end (the bar holds its position unpowered), and TeleOp calls `raise()` at START, not in INIT (G304.H / G403). The positions are placeholders until tuned in `ServoPositionTuner`, one servo at a time.
  - Indicator "lights" are servo-PWM driven. Servo positions map to colors through the constants in each subsystem.
- `common/DebugTelemetry.ENABLED` (default off, Panels): gates every subsystem's and `LaunchReadinessCommand`'s per-loop telemetry readouts (loop time, DS clutter). Tuning OpModes need it on to show those readouts. Logcat event logs are unaffected.
- `common/CrossOpModeStorage`: static fields that keep pose, alliance color, and turret position across OpModes (e.g. auto → teleop). Launch target coordinates are in `common/LaunchTargets` (4 HIVE CELL positions; the `USE_VISION_SELECTOR` flag picks between the nearest-CELL selector with hysteresis and `HiveStateSelector`, which aims at the up CELL tracked by `common/HiveState`; `setForcedCell()` overrides both, used by auto launch steps and cleared by `Incredibot.initTeleop()`/`initAuto()`). Field coordinates are in inches on a 144×144 field.
- `common/BIOBUZZ_Manual_notes.md`: full digest of the BIOBUZZ competition manual (TU07), organized by section and tagged [CODE]/[STRATEGY]/[DERIVED]/[AMBIGUOUS]. Check game rules, field geometry and AprilTag positions here. [DERIVED] values came from the drawings and need verifying.
- `pedro/`: Pedro Pathing setup. `Constants.create()` builds the `Follower` from `PinpointLocalizer`, `Mecanum` and `Foresight`. The Foresight gains in it are already tuned. `pedro/procedures/` holds Pedro's autotune `Procedure` classes (localizer tuners for Pinpoint/OTOS/OctoQuad/two-/three-wheel, mecanum, Foresight, plus `Tests`).
- `opmodes/auto/Poses`: red-frame `{x, y, headingDeg}` values as `@Configurable` `public static double[] RED_*` fields (plus `*_NEEDS_BAR` per intake point), turned into Pedro `Pose`s by lookups on `new Poses(isRed)` and rotated 180° about field center for blue (the field is rotationally symmetric). Lookups take the driver's `Side` (LEFT/RIGHT as seen from behind your alliance wall, so one name means the same place for both alliances; RIGHT = the red values named AUDIENCE, LEFT = those named FAR) and just rotate for blue: `start(Side)`, `launch(LaunchPoint)`, `intakeApproach/intake(IntakePoint)`, `park(Side)` (LEFT/RIGHT end of the LOADING ZONE), and a spline control point per destination. `Side.cell(isRed)` / `Side.of(cell, isRed)` convert to and from the physical AUDIENCE/FAR CELL names that `HiveState` and `LaunchTargets` use. All values are placeholders until measured.
- `opmodes/auto/LaunchPoint` (`LEFT_SPOT_1/2/3`, `RIGHT_SPOT_1/2`, each launching into that side's CELL; `cell(isRed)` gives the physical CELL. LEFT spot 3 is `RED_LAUNCH_FAR_CELL_3` (16, 116, 315), the final-launch spot, partly in the LOADING ZONE; until 2026-11-20 it was LEFT spot 4, and the old LEFT spot 3 (at the rear-wall FLOWER's approach) was removed), `IntakePoint` (GARDEN, alliance-wall FLOWER, side FLOWER; `needsBar()`), `AutoPlan` (static plan edited on the DS: alliance, start side, park side (all LEFT/RIGHT from the driver's view, so a plan carries over between alliances unchanged), launch sequence, intake sequence, each leg a line or spline plus an optional delay after it, and a start delay; survives until the app restarts).
- `opmodes/auto/DynamicAuto`: the match Autonomous, a state machine (`update()` each loop after the scheduler). After the optional start delay it drives to the current launch point. Plan delays (`WAIT` state) run after each launch at a launch point and after each intake point. If that point's CELL is up in `HiveState` (Limelight), it waits for `isReadyToLaunch()` (timeout `READY_TIMEOUT_MS`) and runs `LaunchBallsCommand`. If the CELL is down and it hasn't launched there yet, it waits. Back at a launch point it already launched from, it re-checks the CELL with a Limelight reading taken after arriving or up to `TIP_READING_MAX_AGE_MS` before (none within `TIP_CHECK_TIMEOUT_MS`: assumes a TIP unless `LAUNCH_IF_TIP_UNCONFIRMED`). If the CELL is down after launching there, the HIVE tipped, so it moves to the next launch point (across the HIVE, AROUND by a spline through `Poses.RED_CONTROL_AROUND_HIVE`, or THROUGH by straight lines via the waypoints `RED_THROUGH_HIVE_WAYPOINT_AUDIENCE`/`_FAR` (nearer-to-start first; blue mirrors these across x = 72 instead of rotating), chosen in INIT with the triggers). After each launch it goes to the next intake point (approach, bar down if needed, straight in at `INTAKE_DRIVE_IN_SPEED_FRACTION` speed, until full or `INTAKE_TIMEOUT_MS` (at FLOWERS `FLOWER_WAIT_MS`, since the bar funnels the POLLEN in), and with the bar down it backs straight out to the approach pose and raises the bar. A drive-in or rock leg also ends once the robot stalls (slower than `STALL_SPEED_IN_PER_SEC` for `STALL_MS`), the bar-down back-out ends `BACK_OUT_END_TOLERANCE_IN` early, and a FLOWER is left as soon as the count reads 4. The GARDEN uses no bar (`Poses.GARDEN_NEEDS_BAR = false` since 2026-11-17): approach `RED_GARDEN_APPROACH` (8, 24, 270), straight in to `RED_GARDEN_INTAKE` (8, 9, 270) facing the audience wall, then it rocks from the intake pose (`ROCK_COUNT` 2: back `ROCK_DISTANCE_IN`, forward to the intake pose again), stopping (or skipping it) as soon as the count reads 4, and no back-out), then back to the current launch point. With 0 artifacts it never drives to a launch point (`REFILL_BEFORE_LAUNCH`): after an intake point that picked nothing up, or moving on after a TIP, it goes to the closest unused intake point first (none left: park). To the rear-wall FLOWER from the audience half it always splines through `Poses.RED_CONTROL_SIDE_FLOWER_FROM_AUDIENCE` (12, 110) to clear the HIVE frame (`SIDE_FLOWER_SPLINE_FROM_AUDIENCE`). It parks when a sequence runs out, or in the last `PARK_WINDOW_S` of its own `AUTO_LENGTH_S` clock if it can't launch soon (no artifacts, no launch point left, or waiting at a launch point whose CELL is down); otherwise launching wins: it cuts any intake short (backing out first if the bar is down), goes to the launch point and launches, then parks if there's time. Paths are built from the robot's current pose with `Paths.line`/`Paths.curve` and linear heading, followed directly through the `Follower`; the turret aims via `LaunchTargets.setForcedCell()`. With `FINAL_LAUNCH_AT_LEFT_SPOT_3` (default on), the trip after the last intake point goes in a straight line to LEFT spot 3 for the final launch (don't also put spot 3 in the plan); spot 3 is partly in the LOADING ZONE, so parking within `LEFT_SPOT_3_PARK_RADIUS_IN` of it stays there (`LEFT_SPOT_3_COUNTS_AS_PARK`). After parking it releases the hold after `PARK_RELEASE_MS` (`RELEASE_HOLD_AFTER_PARK`). Pedro holds the pose at every path end (`HOLD_POSITION`, on as on 2026-11-07; false = stop with the motors braked instead, DynamicAuto only). At an intake approach pose it turns in place to the approach heading (`INTAKE_APPROACH_HEADING_TOLERANCE_DEG`) before lowering the bar. `runOpMode()` resets `Constants.foresightConfig.maxPathSpeed`, because a slow path's speed limit stays in that shared static config if a run stops mid-path. Change notes and known issues: `opmodes/auto/README.md`.
- `opmodes/auto/LeftWallAuto`: a fixed Autonomous (no plan editing; INIT: operator B = red, X = blue). From `RED_START_FAR_WALL` it drives to `RED_LAUNCH_FAR_CELL_2`, waits for that CELL (down at the start) to be seen up, launches, intakes at the LEFT FLOWER, comes back and launches again if a recent Limelight reading says the CELL is still up, then parks at `RED_PARK_LEFT` (all red-frame, rotated for blue). Whenever it can't launch it parks there instead. `LeftWallAutoNoFlower` (a subclass, `intakeAtFlower()` false) skips the FLOWER: wait, launch the preloads, park. Both share their timing/speed/TIP-check settings with `DynamicAuto`'s static fields; the log tag is the class name.
- `opmodes/teleop/IncredibotsMecanumDrive`: the match TeleOp (`LinearOpMode`). In INIT it restores the pose from `CrossOpModeStorage` (no Limelight relocalize there any more). At START it restores the turret position (commanding servos during INIT is not allowed, G304.H), calls `Incredibot.initialize(TELEOP, ...)`, then raises the intake bar. Only `DynamicAuto` sets `CrossOpModeStorage.allianceColor`; a TeleOp run without an auto first uses RED (the default).
- `opmodes/tuning/`: pit/bench test OpModes (FlywheelTuner (runs the real TeleOp, tunes the RPM and gain tables per position), FlywheelBenchTuner (fixed-RPM feedforward tuning), FlywheelEncoderTest, TurretAimTest, ServoPositionTuner, IntakeCountTest, SensorTestOpMode, HiveStateTest (stationary, scores Limelight HIVE readings against a truth you enter), HiveDriveTest (drive-only plus Limelight: drive around and watch HiveState, per-tag up/down verdicts with rejection reasons, and a log of HiveState changes; A resets HiveState), LaserIntakeTuner (feed 1-4 balls per trial; records both lasers, replays every trial through `LaserBallCounter` over a grid of thresholds in a background thread, shows the best set and how it holds up at slower loop rates, Y applies it live and logs the values to copy into code; samples go to `laserIntakeTrials.csv`, and RB reloads every saved session's trials (minus saved B discards and `EXCLUDE_TRIALS`) to search over all of them)). All of them are `@Disabled` so they don't show on the Driver Station at competition; remove the annotation from the one you need to use it. Panels is illegal in matches (R704), so these are pit tools only. `FLYWHEEL_TUNING.md` describes the flywheel tuning procedure. `CameraLaunchTuner` (not `@Disabled`, group Tests) is the stationary camera-assisted launch tuner driven by the laptop program in `tools/camera_launch_tuning/` over ADB file exchange; setup in `CAMERA_LAUNCH_TUNING.md`, internals in `tools/camera_launch_tuning/AGENT_GUIDE.md`. It reuses SmartIntakeCommand, LaunchBallsCommand and the flywheel controller (`LaunchSubsystem.updateFlywheelWithGains()`), never registers the drive, and refuses to refill after a burst until the camera review confirms every ball out or the operator presses X (the dead zone above sensor 4 has no sensor).
- `res/xml/biobuzz.xml`: the Robot Controller hardware configuration. Device names must match the string literals in the subsystems.
- New OpModes go under TeamCode with `@TeleOp`/`@Autonomous` (auto should set `preselectTeleOp`); see `TeamCode/.../teamcode/readme.md` for SDK naming conventions.
