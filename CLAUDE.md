# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

FTC (FIRST Tech Challenge) robot controller app for the BIOBUZZ 2026-2027 season, built on the official FTC SDK 12.0. It's an Android app. All team code lives in the `TeamCode` module. `FtcRobotController` is the SDK module and should be left alone except for pulling in upstream SDK updates. Its `external/samples` folder holds reference OpModes you can copy into TeamCode.

## Build

- `./gradlew :TeamCode:assembleDebug` builds the APK. Use this to check that changes compile.
- `./gradlew installDebug` installs to a connected Robot Controller (Control Hub over adb/Wi-Fi).
- There are no unit tests and no lint setup. You can only verify behavior on the physical robot.
- Don't edit `build.common.gradle` or the top-level `build.gradle`; the SDK owns them. Add team dependencies to `TeamCode/build.gradle` or `build.dependencies.gradle`. The latter already has the extra Maven repos (bylazar, dairy.foundation).

## Libraries

- **FTCLib** (`org.ftclib.ftclib:core`): command-based framework. Subsystems extend `SubsystemBase`, and `periodic()` runs each loop through the `CommandScheduler`. Uses FTCLib hardware wrappers (`MotorEx`, `SimpleServo`) and geometry (`Pose2d`, `Rotation2d`, `Translation2d`).
- **Pedro Pathing 3.0** (`com.pedropathing:revhub`, `com.pedropathing:tuning`): path following. Uses its own `com.pedropathing.math.Pose`, which is a different type from FTCLib's `Pose2d`.
- **Panels** (`com.bylazar:fullpanels`): dashboard. `@Configurable` exposes a class's `public static` (non-final) fields for live tuning. Subsystems take a Panels `TelemetryManager` (not the SDK `Telemetry`).

## Architecture

- `Incredibot.java`: the robot container (extends FTCLib `Robot`). Its constructor builds every subsystem and turns on bulk caching for the hubs. `initTeleop()`/`initAuto()` reset the `CommandScheduler`, register the subsystems in order (Drive before Odometry), and set the default commands: `DriveRobotCommand`, `CloseGateCommand` (gate), `SmartIntakeCommand` (intake) and `LaunchReadinessCommand` (launcher). TeleOp binds the operator buttons: X toggles moving-shot compensation, START toggles the turret lock, BACK (hold) reverses the intake, RB runs `LaunchBallsCommand`, Y runs `RelocalizeCommand`, A toggles the intake bar. `initAuto()` sets the preload count to 4 and resets `HiveState`. `DRIVE_ONLY_MODE` (set in Panels before INIT) registers only Drive and Odometry and parks the turret at `TURRET_MID`.
- `subsystems/`: one FTCLib subsystem per mechanism (Drive, Intake, IntakeBar, LaunchGate, Launch, Odometry, Limelight). Each constructor takes `(HardwareMap, TelemetryManager)`, except `OdometrySubsystem`. Hardware device names are string literals in the constructors and must match the Robot Controller configuration on the robot.
  - `DriveSubsystem` runs everything through Pedro's `Follower` (from `pedro/Constants.create()`), which is the only owner of the drive motors and the Pinpoint. Its `periodic()` calls `follower.update()`. `DriveRobotCommand` drives with `follower.manual()` (forward, strafe left, turn CCW). While `LaunchBallsCommand` runs it holds the robot's pose (`follower.hold`) against defense. Moving a stick breaks out of the hold, and `DriveSubsystem.LAUNCH_HOLD_ENABLED` turns the feature off.
  - `OdometrySubsystem` reads the pose from `DriveSubsystem` rather than the Pinpoint. It is constructed with `(DriveSubsystem, TelemetryManager)` and must be registered after `DriveSubsystem` (FTCLib runs `periodic()` in registration order). Its `periodic()` copies the pose, estimates velocity and acceleration, and writes the pose to `CrossOpModeStorage`. Pose resets go through `follower.setPose()`. Pinpoint pod offsets live in `pedro/Constants.localizerConfig`. `updatePoseFromLimelight` applies vision corrections from `RelocalizeWithLimelightCommand`.
  - `LimelightSubsystem` (Limelight 3A, fixed to the chassis) uses each HIVE tag's robot-space position, not MegaTag, because the tags move when a HIVE TIPS. Tag height tells whether a CELL is up or down and updates `HiveState`. Tag geometry is in `common/HiveTags`. `DriveSubsystem.isEffectivelyStationary()` gates when that relocalization runs.
  - `LaunchSubsystem` runs a dual flywheel (PID + `SimpleMotorFeedforward`, RPM converted to ticks/sec using GoBILDA BARE CPR) and a turret servo (goBILDA 5-turn, 1800°, `GEAR_RATIO = 82/24`). Above `FLYWHEEL_BANG_BANG_THRESHOLD_RPM` below target it runs bang-bang. Feedforward is voltage-compensated. Gains come from a gain table indexed by distance (`GAIN_TABLE_*`). There is no adjustable visor/hood. `LaunchReadinessCommand` runs every loop: it picks the target, leads it for moving shots when enabled, aims the turret, spins the flywheel from the `SHOT_DISTANCES_IN`/`SHOT_RPMS` table, and calls `setShotSolutionReady`/`setShotPossible`. Servos give no feedback, so it decides the turret has settled from an estimate based on `TURRET_SERVO_RPM`. The turret check inside `isReadyToLaunch()` always passes because it compares the commanded position to itself. `periodic()` sets the alignment indicator light from the result.
  - `IntakeSubsystem` drives the intake motor and the transfer motor (the sweeper servos were removed). Four debounced beam breaks feed the artifact count (see its class comment), and it stops itself when full (`MAX_ARTIFACTS = 4`). `SmartIntakeCommand` switches between the LAUNCHING, INTAKING and FULL states based on whether the gate is open. `LaunchBallsCommand` opens the gate until the robot is empty. Every launch starts with a kick: the transfer reverses briefly (`KICK_REVERSE_MS_BY_COUNT`, shorter for more artifacts) while the intake runs forward to keep the stack in, then feeds forward at full power. Counting ignores sensor-1 edges and the jam rule while launching. Sensor states only update inside `periodic()`, so test OpModes must call it.
  - `IntakeBarSubsystem` uses two mirrored positional servos (`intakeBarLeftServo`/`intakeBarRightServo`, the former sweeper ports) to drop a bar in front of the robot for pulling POLLEN out of a FLOWER's bottom opening (G418: POLLEN only). Each servo has its own RAISED/LOWERED positions, and `setBarFraction()` moves both by the same fraction so they don't fight. TeleOp calls `raise()` in INIT to hold the bar up; that is legal only because the bar already rests there (G403 allows re-holding a position, not moving). The positions are placeholders until tuned in `ServoPositionTuner`, one servo at a time.
  - Indicator "lights" are servo-PWM driven. Servo positions map to colors through the constants in each subsystem.
- `common/CrossOpModeStorage`: static fields that keep pose, alliance color, and turret position across OpModes (e.g. auto → teleop). Launch target coordinates are in `common/LaunchTargets` (4 HIVE CELL positions; the `USE_VISION_SELECTOR` flag picks between the nearest-CELL selector with hysteresis and `HiveStateSelector`, which aims at the up CELL tracked by `common/HiveState`). Field coordinates are in inches on a 144×144 field.
- `common/BIOBUZZ_Manual_notes.md`: full digest of the BIOBUZZ competition manual (TU07), organized by section and tagged [CODE]/[STRATEGY]/[DERIVED]/[AMBIGUOUS]. Check game rules, field geometry and AprilTag positions here. [DERIVED] values came from the drawings and need verifying.
- `pedro/`: Pedro Pathing setup. `Constants.create()` builds the `Follower` from `PinpointLocalizer`, `Mecanum` and `Foresight`. The Foresight gains in it are already tuned. `pedro/procedures/` holds Pedro's autotune `Procedure` classes (localizer tuners for Pinpoint/OTOS/OctoQuad/two-/three-wheel, mecanum, Foresight, plus `Tests`).
- `common/Poses`: Pedro `Pose`s written for red, rotated 180° about field center for blue (the field is rotationally symmetric). Holds `RELOCALIZE_STANCE` for `RelocalizeCommand`.
- `opmodes/teleop/IncredibotsMecanumDrive`: the match TeleOp (`LinearOpMode`). In INIT it restores the pose from `CrossOpModeStorage` and schedules `RelocalizeWithLimelightCommand` (off by default via `ENABLED`). At START it restores the turret position (commanding servos during INIT is not allowed, G304.H), then calls `Incredibot.initialize(TELEOP, ...)`. Nothing sets `CrossOpModeStorage.allianceColor` yet, so it is always RED (the default).
- `opmodes/tuning/`: pit/bench test OpModes (FlywheelTuner, FlywheelEncoderTest, TurretAimTest, ServoPositionTuner, IntakeCountTest, SensorTestOpMode, HiveStateTest; ServoWithEncoderTest is `@Disabled`). Panels is illegal in matches (R704), so these are pit tools only. `FLYWHEEL_TUNING.md` describes the flywheel tuning procedure.
- `res/xml/biobuzz.xml`: the Robot Controller hardware configuration. Device names must match the string literals in the subsystems.
- No Autonomous OpMode exists yet (`Incredibot.initAuto()` is ready for one). New OpModes go under TeamCode with `@TeleOp`/`@Autonomous` (auto should set `preselectTeleOp`); see `TeamCode/.../teamcode/readme.md` for SDK naming conventions.
