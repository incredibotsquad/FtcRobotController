# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

FTC (FIRST Tech Challenge) robot controller app for the BIOBUZZ 2026-2027 season, built on the official FTC SDK 12.0. It's an Android app. All team code lives in the `TeamCode` module. `FtcRobotController` is the SDK module and should be left alone except for pulling in upstream SDK updates. Its `external/samples` folder holds reference OpModes you can copy into TeamCode.

## Build

- `./gradlew :TeamCode:assembleDebug` builds the APK. Use this to check that changes compile.
- `./gradlew installDebug` installs to a connected Robot Controller (Control Hub over adb/Wi-Fi).
- There are no unit tests and no lint setup. You can only verify behavior on the physical robot.
- Don't edit `build.common.gradle` or the top-level `build.gradle`; the SDK owns them. Add team dependencies to `TeamCode/build.gradle` or `build.dependencies.gradle`. The latter already has the extra Maven repos (bylazar, dairy.foundation).

## Libraries

- **FTCLib** (`org.ftclib.ftclib:core`): command-based framework. Subsystems extend `SubsystemBase`, and `periodic()` runs each loop through the `CommandScheduler`. Uses FTCLib hardware wrappers (`MotorEx`, `SimpleServo`) and geometry (`Pose2d`, `Rotation2d`, `Translation2d`).
- **Pedro Pathing 3.0** (`com.pedropathing:revhub`, `com.pedropathing:tuning`): path following. Uses its own `com.pedropathing.math.Pose`, which is a different type from FTCLib's `Pose2d`.
- **Panels** (`com.bylazar:fullpanels`): dashboard. `@Configurable` exposes a class's `public static` (non-final) fields for live tuning. Subsystems take a Panels `TelemetryManager` (not the SDK `Telemetry`).

## Architecture

- `Incredibot.java`: the robot container (extends FTCLib `Robot`). Its constructor builds every subsystem and turns on bulk caching for the hubs. `initTeleop()`/`initAuto()` reset the `CommandScheduler`, register the subsystems in order (Drive before Odometry), and set the default commands: `DriveRobotCommand`, `CloseGateCommand` (gate), `SmartIntakeCommand` (intake) and `LaunchReadinessCommand` (launcher). TeleOp binds the operator buttons: X toggles moving-shot compensation, START toggles the turret lock, BACK (hold) reverses the intake, RB runs `LaunchBallsCommand`, Y runs `RelocalizeCommand` (resets the pose to the stance in the corner nearest the odometry position, heading 0 or 180), A toggles the intake bar. `initAuto()` sets the preload count to 4 and resets `HiveState`. `DRIVE_ONLY_MODE` (set in Panels before INIT) registers only Drive and Odometry and parks the turret at `TURRET_MID`.
- `subsystems/`: one FTCLib subsystem per mechanism (Drive, Intake, IntakeBar, LaunchGate, Launch, Odometry, Limelight). Each constructor takes `(HardwareMap, TelemetryManager)`, except `OdometrySubsystem`. Hardware device names are string literals in the constructors and must match the Robot Controller configuration on the robot.
  - `DriveSubsystem` runs everything through Pedro's `Follower` (from `pedro/Constants.create()`), which is the only owner of the drive motors and the Pinpoint. Its `periodic()` calls `follower.update()`. `DriveRobotCommand` drives with `follower.manual()` (forward, strafe left, turn CCW). While `LaunchBallsCommand` runs it holds the robot's pose (`follower.hold`) against defense. Moving a stick breaks out of the hold, and `DriveSubsystem.LAUNCH_HOLD_ENABLED` turns the feature off.
  - `OdometrySubsystem` reads the pose from `DriveSubsystem` rather than the Pinpoint. It is constructed with `(DriveSubsystem, TelemetryManager)` and must be registered after `DriveSubsystem` (FTCLib runs `periodic()` in registration order). Its `periodic()` copies the pose, estimates velocity and acceleration, and writes the pose to `CrossOpModeStorage`. Pose resets go through `follower.setPose()`. Pinpoint pod offsets live in `pedro/Constants.localizerConfig`. `updatePoseFromLimelight` applies vision corrections from `RelocalizeWithLimelightCommand`.
  - `LimelightSubsystem` (Limelight 3A, fixed to the chassis) uses each HIVE tag's robot-space position, not MegaTag, because the tags move when a HIVE TIPS. Tag height tells whether a CELL is up or down and updates `HiveState`. Tag geometry is in `common/HiveTags`. `DriveSubsystem.isEffectivelyStationary()` gates when that relocalization runs.
  - `LaunchSubsystem` runs a dual flywheel (PID + `SimpleMotorFeedforward`, RPM converted to ticks/sec using GoBILDA BARE CPR) and a turret servo (goBILDA 5-turn, 1800°, `GEAR_RATIO = 82/24`). Above `FLYWHEEL_BANG_BANG_THRESHOLD_RPM` below target it runs bang-bang. Feedforward is voltage-compensated. Gains come from a gain table indexed by distance (`GAIN_TABLE_*`). There is no adjustable visor/hood. `LaunchReadinessCommand` runs every loop: it picks the target, leads it for moving shots when enabled, aims the turret, spins the flywheel from the `SHOT_DISTANCES_IN`/`SHOT_RPMS` table (outside it, the end RPM is used and the shot still counts as ready), and calls `setShotSolutionReady`/`setShotPossible`. Servos give no feedback, so it decides the turret has settled from an estimate based on `TURRET_SERVO_RPM`. The turret check inside `isReadyToLaunch()` always passes because it compares the commanded position to itself. `periodic()` sets the alignment indicator light from the result.
  - `IntakeSubsystem` drives the intake motor and the transfer motor (the sweeper servos were removed). Four debounced beam breaks feed the artifact count (see its class comment), and it stops itself when full (`MAX_ARTIFACTS = 4`). The settle corrections may only raise the count unless `ALLOW_SETTLED_DECREASE` (default off: an undercount would let in a 5th, G407), except that a launch hitting `MAX_FIRE_MS` resets the count to 0 if the transfer fed forward with all sensors clear for `EMPTY_CONFIRM_MS` (`confirmEmptyAfterLaunch()`); every count change is logged with tag `IntakeCount`. The intake motor (not the transfer) has a `StallGuard`: a stall (current ≥ `STALL_CURRENT_A`, or low encoder speed with `STALL_SIGNAL = VELOCITY`) for `STALL_TIME_MS` while commanded forward and not launching reverses it for `UNJAM_REVERSE_MS`, up to `UNJAM_MAX_TRIES` per `UNJAM_WINDOW_MS`, then pauses `UNJAM_GIVE_UP_MS`. Intake-motor writes go through the guard (`request()`), so commands' powers are reapplied after an unjam; stop/reverse requests cancel it. Logged with tag `IntakeStall`. `SmartIntakeCommand` switches between the LAUNCHING, INTAKING and FULL states based on whether the gate is open. `LaunchBallsCommand` commands the intake bar up (without waiting for it) and keeps it up during the launch, and opens the gate until the robot is empty. Every launch starts with a kick: the transfer reverses briefly (`KICK_REVERSE_MS_BY_COUNT`, shorter for more artifacts) while the intake runs forward to keep the stack in, then feeds forward at full power. Counting ignores sensor-1 edges and the jam rule while launching. Sensor states only update inside `periodic()`, so test OpModes must call it.
  - `IntakeBarSubsystem` uses two mirrored positional servos (`intakeBarLeftServo`/`intakeBarRightServo`, the former sweeper ports) to drop a bar in front of the robot for pulling POLLEN out of a FLOWER's bottom opening (G418: POLLEN only). Each servo has its own RAISED/LOWERED positions, and `setBarFraction()` moves both by the same fraction so they don't fight. TeleOp calls `raise()` in INIT to hold the bar up; that is legal only because the bar already rests there (G403 allows re-holding a position, not moving). The positions are placeholders until tuned in `ServoPositionTuner`, one servo at a time.
  - Indicator "lights" are servo-PWM driven. Servo positions map to colors through the constants in each subsystem.
- `common/CrossOpModeStorage`: static fields that keep pose, alliance color, and turret position across OpModes (e.g. auto → teleop). Launch target coordinates are in `common/LaunchTargets` (4 HIVE CELL positions; the `USE_VISION_SELECTOR` flag picks between the nearest-CELL selector with hysteresis and `HiveStateSelector`, which aims at the up CELL tracked by `common/HiveState`; `setForcedCell()` overrides both, used by auto launch steps and cleared by `Incredibot.initTeleop()`/`initAuto()`). Field coordinates are in inches on a 144×144 field.
- `common/BIOBUZZ_Manual_notes.md`: full digest of the BIOBUZZ competition manual (TU07), organized by section and tagged [CODE]/[STRATEGY]/[DERIVED]/[AMBIGUOUS]. Check game rules, field geometry and AprilTag positions here. [DERIVED] values came from the drawings and need verifying.
- `pedro/`: Pedro Pathing setup. `Constants.create()` builds the `Follower` from `PinpointLocalizer`, `Mecanum` and `Foresight`. The Foresight gains in it are already tuned. `pedro/procedures/` holds Pedro's autotune `Procedure` classes (localizer tuners for Pinpoint/OTOS/OctoQuad/two-/three-wheel, mecanum, Foresight, plus `Tests`).
- `opmodes/auto/Poses`: red-frame `{x, y, headingDeg}` values as `@Configurable` `public static double[] RED_*` fields (plus `*_NEEDS_BAR` per intake point), turned into Pedro `Pose`s by lookups on `new Poses(isRed)` and rotated 180° about field center for blue (the field is rotationally symmetric). Lookups take field-side names and handle the rotation: `start(audienceWall)`, `launch(LaunchPoint)`, `intakeApproach/intake(IntakePoint)`, `park(towardAudience)` (LEFT/RIGHT end of the LOADING ZONE), and a spline control point per destination. All values are placeholders until measured.
- `opmodes/auto/LaunchPoint` (2 spots per CELL, CELL named by field side as in `HiveState`), `IntakePoint` (GARDEN, alliance-wall FLOWER, side FLOWER; `needsBar()`), `AutoPlan` (static plan edited on the DS: alliance, start wall, park spot (LEFT toward the far wall / RIGHT toward the audience wall), launch sequence, intake sequence, each leg a line or spline plus an optional delay after it, and a start delay; survives until the app restarts).
- `opmodes/auto/DynamicAuto`: the match Autonomous, a state machine (`update()` each loop after the scheduler). After the optional start delay it drives to the current launch point. Plan delays (`WAIT` state) run after each launch at a launch point and after each intake point. If that point's CELL is up in `HiveState` (Limelight), it waits for `isReadyToLaunch()` (timeout `READY_TIMEOUT_MS`) and runs `LaunchBallsCommand`. If the CELL is down and it hasn't launched there yet, it waits. If the CELL is down after launching there, the HIVE tipped, so it moves to the next launch point (across the HIVE, by a spline through `Poses.RED_CONTROL_AROUND_HIVE` (one control point) or `RED_CONTROL_THROUGH_HIVE_1`/`_2` (two, ordered nearer-to-start first), chosen in INIT with the triggers). After each launch it goes to the next intake point (approach, bar down if needed, straight in at `INTAKE_DRIVE_IN_SPEED_FRACTION` speed, until full or `INTAKE_TIMEOUT_MS` (at FLOWERS `FLOWER_WAIT_MS`, since the bar funnels the POLLEN in), and with the bar down it backs straight out to the approach pose; at the GARDEN, with `GARDEN_PUSH_ENABLED` (default on, experimental) it raises the bar and drives straight back in to `GARDEN_PUSH_PAST_IN` past the intake pose at the drive-in speed (stops when full or after `GARDEN_PUSH_TIMEOUT_MS`); with it off it rocks forward/back `ROCK_COUNT` times (`ROCK_DISTANCE_IN` forward from where it stopped, along X when facing 0/180 and Y when facing 90/270) to pull in the elements the bar holds, stopping early (or skipping it) as soon as the robot is full, then raises the bar), then back to the current launch point. It parks when a sequence runs out, or in the last `PARK_WINDOW_S` of its own `AUTO_LENGTH_S` clock unless a launch is in progress or the robot is ready to launch at a confirmed-up CELL (then right after that launch). Paths are built from the robot's current pose with `Paths.line`/`Paths.curve` and linear heading, followed directly through the `Follower`; the turret aims via `LaunchTargets.setForcedCell()`.
- `opmodes/teleop/IncredibotsMecanumDrive`: the match TeleOp (`LinearOpMode`). In INIT it restores the pose from `CrossOpModeStorage` and schedules `RelocalizeWithLimelightCommand` (off by default via `ENABLED`). At START it restores the turret position (commanding servos during INIT is not allowed, G304.H), then calls `Incredibot.initialize(TELEOP, ...)`. Only `DynamicAuto` sets `CrossOpModeStorage.allianceColor`; a TeleOp run without an auto first uses RED (the default).
- `opmodes/tuning/`: pit/bench test OpModes (FlywheelTuner (runs the real TeleOp, tunes the RPM and gain tables per position), FlywheelBenchTuner (fixed-RPM feedforward tuning), FlywheelEncoderTest, TurretAimTest, ServoPositionTuner, IntakeCountTest, SensorTestOpMode, HiveStateTest (stationary, scores Limelight HIVE readings against a truth you enter), HiveDriveTest (drive-only plus Limelight: drive around and watch HiveState, per-tag up/down verdicts with rejection reasons, and a log of HiveState changes; A resets HiveState); ServoWithEncoderTest is `@Disabled`). Panels is illegal in matches (R704), so these are pit tools only. `FLYWHEEL_TUNING.md` describes the flywheel tuning procedure.
- `res/xml/biobuzz.xml`: the Robot Controller hardware configuration. Device names must match the string literals in the subsystems.
- New OpModes go under TeamCode with `@TeleOp`/`@Autonomous` (auto should set `preselectTeleOp`); see `TeamCode/.../teamcode/readme.md` for SDK naming conventions.
