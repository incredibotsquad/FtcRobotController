Moving Shot Compensation Tuning Guide

This guide explains the optional shooting-on-the-move code, what it changes, how the math works, and which values should be tested and tuned before making it the normal competition path.

What Changed

The robot now has an optional moving-shot path. It is controlled by this flag: 

LaunchReadinessCommand.ENABLE_MOVING_SHOT_COMPENSATION = false;
The flag defaults to false, so the robot still uses the original static pose-based shot behavior unless the team explicitly enables moving-shot compensation.

Files Changed

  • OdometrySubsystem.java: estimates robot velocity and acceleration.
  • LaunchReadinessCommand.java: computes static and moving shot solutions.
  • LaunchSubsystem.java: adds a shot-solution readiness gate.
  • AutoFireCommand.java: adds zone-specific speed limits when moving mode is enabled.

Design Goal

Keep the existing shot code safe and available, while adding a testable alternate path that accounts for robot translational velocity.

High-Level Flow

1. Read Pose

Pinpoint provides X, Y, and heading in OdometrySubsystem.periodic().

2. Estimate Velocity

Velocity is calculated from pose change divided by loop time.

3. Calculate Shots

LaunchReadinessCommand calculates both static and moving shot solutions.

4. Apply Active Mode

The static solution is used unless moving-shot compensation is enabled.

5. Gate Fire

AutoFireCommand opens the gate only if zone, readiness, and speed checks pass.

Velocity Calculation

Velocity is calculated in OdometrySubsystem from the Pinpoint pose stream. It does not depend on Pedro Pathing, so it works in TeleOp and Autonomous. 

fieldVelocity = new Translation2d(
    (newPose.getX() - previousPose.getX()) / dtSeconds,
    (newPose.getY() - previousPose.getY()) / dtSeconds
);

This produces field-relative velocity in inches per second:

  • vx: robot speed along the field X axis.
  • vy: robot speed along the field Y axis.
  • speed: sqrt(vx^2 + vy^2).
fieldAcceleration = new Translation2d(
    (fieldVelocity.getX() - previousVelocity.getX()) / dtSeconds,
    (fieldVelocity.getY() - previousVelocity.getY()) / dtSeconds
);

Acceleration is also estimated, but the first moving-shot version does not use it for control. It is available for future filtering or more advanced prediction.

Velocity based on raw pose differences can be noisy. Watch telemetry while the robot is stopped: speed should be close to zero. If it jitters too much, add filtering before trusting high-speed shots.

Shot Estimation Logic

Static Shot

The original static shot aims directly at the real target coordinate: 

target = (TARGET_X, TARGET_Y)

From that target, the code calculates:

  • Distance to target.
  • Turret angle relative to robot heading.
  • Turret servo position.
  • Flywheel constants from the distance lookup table.
  • Visor position, currently fixed to LAUNCH_VISOR_LOW.

Moving Shot

The moving shot shifts the aim target opposite the robot's field-relative velocity. This is a first-order compensation for the ball inheriting robot velocity when launched. 

compensationTime = estimatedFlightTime + BURST_MIDPOINT_SECONDS
compensatedTargetX = TARGET_X - velocityX * compensationTime
compensatedTargetY = TARGET_Y - velocityY * compensationTime

Then the same turret/RPM/visor calculation is run against the compensated target.

Example: if the robot is moving +X at 20 in/s and compensation time is 0.5 s, the compensated target moves 10 inches in the -X direction. The turret aims slightly behind the true goal so the ball's inherited robot velocity carries it toward the goal.

Why Burst Timing Matters

Opening the launch gate releases all three balls. That means the shot is a burst, not three individually-aimed shots. The robot may move between ball 1, ball 2, and ball 3.

The code uses BURST_MIDPOINT_SECONDS to aim for the middle of the burst. This tries to balance the error across all three balls rather than perfectly optimizing only the first ball. 

compensationTime = flightTime + burstMidpoint
If all three balls spread in the direction of robot travel, tune burst midpoint and speed caps before increasing aggression.

Tunable Variables

Variable Current Value Where Meaning How To Tune
ENABLE_MOVING_SHOT_COMPENSATION false LaunchReadinessCommand Master switch for moving-shot compensation. Keep false while validating telemetry. Turn true only during controlled testing.
SHOT_FLIGHT_BASE_SECONDS 0.25 LaunchReadinessCommand Base estimate for how long a ball is in flight. Increase if shots miss in the direction of robot travel. Decrease if they miss opposite travel.
SHOT_FLIGHT_SECONDS_PER_INCH 0.0035 LaunchReadinessCommand Additional flight time added per inch of distance. Tune after base time. Increase if longer shots need more lead than shorter shots.
BURST_MIDPOINT_SECONDS 0.175 LaunchReadinessCommand Extra time to aim for the middle of the three-ball release. Measure or estimate the time from gate open to the middle ball exiting. Tune for tightest 3-ball group.
MAX_COMPENSATED_SPEED_IPS 24.0 LaunchReadinessCommand Global speed safety limit for declaring a moving shot solution ready. Start lower if shots are inconsistent. Raise only after the math is proven.
MAX_TARGET_LEAD_INCHES 18.0 LaunchReadinessCommand Maximum distance the target may be shifted for compensation. If this trips often, the robot is moving too fast or the time estimates are too high.
CLOSE_ZONE_MAX_MOVING_SHOT_SPEED_IPS 18.0 AutoFireCommand Auto-fire speed cap in the large goal-side launch zone. Start around 8-10 in/s for first tests, then raise if consistency is good.
FAR_ZONE_MAX_MOVING_SHOT_SPEED_IPS 6.0 AutoFireCommand Auto-fire speed cap in the small audience-side launch zone. Keep conservative. This zone is small, so the legal window is short.
LOOKUP_TABLE 75, 95, 115, 130 in entries LaunchReadinessCommand Distance-to-flywheel constants table. Tune static shots first. Moving shot uses effective compensated distance through the same table.

Safety and Readiness Gates

A moving shot is only considered ready when all normal launcher checks pass and the shot solution is safe. 

shotSolutionReady =
    robotSpeedIps <= MAX_COMPENSATED_SPEED_IPS
    && leadDistanceInches <= MAX_TARGET_LEAD_INCHES
    && !turretTargetClamped;

LaunchSubsystem.isReadyToLaunch() now includes this readiness flag: 

return flywheelReady && turretReady && visorReady && shotSolutionReady;

In AutoFireCommand, moving mode also has zone-specific speed limits: 

close zone speed cap = 18 in/s
far zone speed cap   = 6 in/s
Manual firing currently opens the gate through LaunchBallsCommand. If that command does not check isReadyToLaunch(), manual fire can still release balls even when the moving shot solution is not ready.

Telemetry To Watch

Telemetry What It Means Good Sign
Odometry: Speed Current robot translational speed in inches/sec. Near zero when stopped; smooth changes while driving.
Shot Mode Whether static or moving solution is active. STATIC during baseline tests, MOVING during moving tests.
Shot Ready Whether the selected shot solution passes readiness checks. True only when speed, lead, turret, visor, and flywheel are acceptable.
Moving Shot Lead Inches How far the aim point is shifted from the real goal. Small at low speed. Grows with speed and distance.
Moving Shot Angle Delta Difference between moving-compensated aim angle and static aim angle. Changes direction when robot drives the opposite way.
Moving Shot RPM Delta Difference between moving-compensated RPM and static RPM. Usually smaller than angle delta; should not jump wildly.
Moving Shot Turret Clamped Whether the calculated turret target exceeded mechanical limits. False. If true, do not trust that shot.

Testing Plan

  1. Deploy with ENABLE_MOVING_SHOT_COMPENSATION = false.
  2. Drive without shooting and confirm velocity telemetry is reasonable.
  3. Run normal static shots while stopped. Confirm no regression.
  4. Watch moving-shot telemetry while static mode is still active.
  5. Enable moving mode only after telemetry looks believable.
  6. Test in the large close/goal-side zone first at very low speed.
  7. Lower CLOSE_ZONE_MAX_MOVING_SHOT_SPEED_IPS if spread is too large.
  8. Tune BURST_MIDPOINT_SECONDS to tighten the 3-ball burst.
  9. Tune flight time constants only after burst timing looks reasonable.
  10. Keep the small far/audience-side zone conservative until close-zone shots are reliable.
The fastest path to consistency is to make static shots excellent first, then add moving compensation slowly with speed caps.

Tuning Symptoms

Symptom Likely Cause Adjustment
Shots miss in the direction the robot is moving. Not enough lead time. Increase BURST_MIDPOINT_SECONDS or flight time.
Shots miss opposite the direction the robot is moving. Too much lead time. Decrease BURST_MIDPOINT_SECONDS or flight time.
Ball 1 and ball 3 spread too far apart. Robot is moving too fast during the burst. Lower zone speed caps or shorten gate-open/burst duration mechanically.
Auto-fire will not open the gate in moving mode. Speed too high, lead too high, turret clamped, or flywheel not ready. Check Shot Ready, speed, lead inches, and turret clamped telemetry.
Velocity telemetry jumps while stopped. Pose noise or loop timing noise. Add velocity filtering before raising shot speed caps.

Recommended Competition Defaults

  • Keep ENABLE_MOVING_SHOT_COMPENSATION available as a quick disable switch.
  • Use moving compensation first in the large goal-side launch zone.
  • Keep far/audience-side zone speed very low because the zone is small.
  • Do not raise speed caps until the 3-ball burst is consistent at lower speeds.
  • Before making moving mode the default, confirm manual and auto shooting both respect readiness.
